# 新任务开发经验总结（真机踩坑录）

> 来源：`xyz-shelbynet`（Shelby Explorer 上传任务）从零实现 + 100 窗口真机批量验证全流程。
> 写新任务前先读本文件，能省下大量真机往返。

## 1. 真机核实是唯一标准，选择器先猜后验

- SPA 站点的静态 HTML 看不到登录后的内容：初始选择器必然靠猜，写完立刻 `task:run` 单窗口真跑，按截图/日志迭代。
- 真机核实结论必须写进任务文件头注释 + `meta.note`（含核实日期），这是后续排障的第一手资料。
- 每个断言失败都有截图（`data/screenshots/<日期>/<窗口ID>/<任务key>/`），先看图再改码。

## 2. 登录态判定：别用全页文本

- 首页表格/数据里可能全是 `0x` 开头内容（区块链站常见）——`textPresent('0x')` 必误判。
- 正确做法：用**范围选择器**（如 `header button:has-text("0x")`）自建竞速循环（`ctx.visible` 轮询 + reload 兜底），不要用 `detectPageState` 的全页文案判定。
- SPA 渲染有 0-3s 延迟，首轮竞速至少 20s。

## 3. 钱包弹窗三个坑

1. **静默连接**：扩展已授权的窗口，点站内 Connect 后可能根本不弹钱包弹窗——`loginByWallet` 抛「钱包弹窗未出现」必须**容忍**，登录结果以页面登录态为准，不能判失败。
2. **弹窗渲染慢 / 点击未注册**：高并发 + 慢代理下，点了 Connect Wallet 弹窗 30s+ 不出（真机实测两轮都失败过）。补点自愈模式：
   - 预算放宽到 45s+；
   - **目标按钮仍可见才补点**（弹窗遮罩出现说明点击已生效，此时补点会误点遮罩把弹窗关掉）；
   - 每轮 reload/等待都要打日志，别静默循环。
3. 网络切换：任务上线前真机确认钱包网络是否已在目标链；若站点不自动发起 switchNetwork，需在钱包扩展 UI 里加切链步骤。

## 4. 文件上传两个坑

1. **隐藏 file input**：`display:none` 的 input 不能用 `waitFor visible`，用 DOM 挂载判定（`locator.count() > 0` 轮询）；`setInputFiles` 对隐藏 input 可用。
2. **一次性文件（blob 名查重）**：站点可能在选完文件后立即查重——已上传的文件弹窗直接报错（如 `Blob name already taken`）且提交按钮**永不启用**。必须把该错误文案短路视为「已上传=成功」（幂等收敛），绝不能等按钮启用、更不能当失败重试。

## 5. 任务卡死：先自己看日志，别盲目重跑（最重要）

- 卡死第一反应：`data/logs/app.log` 最新日志 + 对应窗口截图目录。日志「静默期」本身是线索——说明卡在某个不打日志的等待循环（reload 循环、CDP 连接、窗口开合）。
- 真机实况：某窗口一次尝试静默卡 15 分钟（代理/会话坏），直到任务超时兜底才暴露。**每类等待循环必须打日志**，否则批量卡死时无从定位。
- **明确标准：真机运行连续 2 次失败或 10 分钟无进展 → 立刻停下，带着日志+截图找用户请求人工接入**（问窗口状态、代理、站点是否改版），不要继续派自动化重跑消耗时间。
- 反复开合过的窗口（task:run 调试多次）代理/会话可能变差：验证换一个新窗口，别跟旧窗口死磕。
- 开窗失败（比特浏览器 API 瞬时错误）会跳过不重试——重触发一次即可，属环境抖动不是任务 bug。

## 6. 运维要点

- 后端 `tsx src/index.ts` **无 watch**：改完任务代码必须重启 dev 才生效；重启会打断在途窗口会话，批量运行中不要重启。
- 单窗口触发：`POST /api/tasks/:key/trigger` + body `{"bitbrowserId":"<id>"}`（`immediate`，不等待错峰）；批量触发不带 body（全部启用窗口）。
- 结果核对：`GET /api/batches` 的 `stats`（total/success/failed/skipped）；每窗口今日成功数直接查 SQLite `runs` 表（`task_key + date + status='success'` 按 profile_id 分组）。
- 熔断（连续 2 次失败当日 skip）修复后可 `POST /api/profiles/:id/breaker/reset` 复位；旧代码 bug 导致的熔断要主动复位。
- 任务 key 全局唯一，登记 `src/tasks/index.ts` ALL 数组；面板「定时任务」引用新 key 需手动新建计划。

## 7. 性能参数建议（真机校准）

- `retry.backoffSec` 60s 即可（瞬时问题重试快）；瞬时失败重试通常一次就过。
- `timeoutSec` 给真实最慢路径留 2 倍余量即可，别给 15 分钟——卡死窗口会白白占住并发槽。
- 卡死类等待（登录态竞速 reload 轮数）收敛到 3-4 轮，每轮打日志。

## 8. reCAPTCHA 九宫格模拟点击（rev2 已归档，现行实现见第 9 节；Arc 领水真机，2026-09-09）

1. **多 anchor 错选**：页面常驻 v3 anchor iframe（sitekey A），v2 挑战时动态插入另一个 anchor（sitekey B）。`page.frames()` 取第一个匹配会选到 v3——点它**无任何效果**（复选框不弹挑战，静默失败）。必须按 URL 的 `k=` 参数排除常驻 v3 sitekey（`ctx.solveRecaptchaGrid({ siteKeyExclude })`），bframe 查找同样要排除。
2. **提示语读取过早**：bframe 注入后网格 DOM 可能尚未渲染，`.rc-imageselect-desc-wrapper strong` 首读为空 → 误抛「九宫格提示文字未找到」。读提示语要轮询重试（10s / 500ms），非空才继续。
3. **点击未注册要自愈不要吞**：偶发点击未注册时，下一轮循环能自我纠正；anchor 点击失败记 warn 继续流程，别静默 `catch(() => {})` 吞掉排障线索。
4. **classification 的 confidence 是坑**：传 `confidence: 0.5` 会返回「全部 ≥0.5 的格子」，可能少于 3 个——Google 每轮**至少要求点 3 格**，少于 3 格点验证无效、必刷新一轮（真机 5 轮全败的根因之一）。不传 confidence 用平台默认「排名前三」恰好满足最少 3 格。
5. **点格节奏要随机**：固定 2s 间隔太程序化，Google 会判定机器人刷新挑战；点格/验证后等待用 1.5-2.5s / 2.5-3.5s 随机抖动。
6. **真机验证结论（2026-09-09，窗口 99）**：任务全链路成功（20 testnet USDC 领取成功 + 成功截图），但该次 v3 评分直接通过、**未触发九宫格挑战**——九宫格模拟点击路线仍待下一次真正触发挑战时验证。同期教训：① 窗口 100 连续 2 次失败当日熔断（含手动全部 skipped），验证烧窗口前先想清楚；② 窗口 99 首跑「提交按钮 15s 未变为可用」= 首次加载地址 fill 后按钮未启用（页面 JS 未就绪偶发），自动重试恢复——此类偶发交给重试机制即可，别急着修代码。
7. **批量验证最终结论（2026-09-09，15 窗口）**：成功 8 窗口（99/98/96/94/92/91/87/86），模式高度一致——**v3 直过**或「挑战失败 → 自动重试 → 新会话 v3 直过」；九宫格挑战本身自动化 0 通过。三层原因：① yescaptcha 分类对 **4x4 网格识别能力弱**（3x3 明显更准；4x4 常返回空数组/全勾/GARBAGE_SAMPLE），多轮循环+reload 换图只能缓解；② Google 对同会话连续 verify 失败有风控（用户实操也需多次验证/隔段时间才过）；③ 挑战期提交按钮禁用等 widget 回调，任何未完成的选择点 verify 都判错。**务实结论（rev3 已部分推翻：容器截图本身即分类乱跳根因，「截图确认无误」判断已作废；现行实现改用原生整图，见第 9 节）**：九宫格路线保留（rev2 截图方案已废弃、拟人点击/稳定等待/换图重试齐备），但挑战窗口的真实通过率主要靠重试后的新会话 v3 直过——meta.retry 2 次 + backoffSec 120 的既有配置即是主防线；若未来分类平台支持 4x4 更强识别可回炉再测。教训：真机调试截图落盘到 data/screenshots/grid-debug 是定位「图对还是分类错」的关键手段（用户肉眼确认截图正确后，立刻把方向从截图修复转向风控应对，少走弯路）；单测里 fs 写盘必须 mock，否则数百张测试图污染诊断目录。
8. **dynamic-selected 必须二次确认（真机诊断，2026-09-09）**：现代 reCAPTCHA 点击格子后 class 分两类——`tileselected`（直接选中）与 `dynamic-selected`（图片刷新中，刷新 1-6 秒完成后**必须再点一次确认**才算选中）。旧实现按 img src 变化做小图二次识别，但 src 监测抓不到该刷新 → 从未确认 → Google 判选择未完成 → 每轮 select-more → 九宫格 0 通过。修复：选点判定**以 td class 为准、不再依赖 src**——点击后等 1.5-2.5s 稳定再读 class；含 dynamic-selected 轮询等其消失（最多 8s/500ms）→ 拟人确认点击 → 再读 class 判定（仍 dynamic 再确认，最多 2 轮）；无 selected 字样记 warn 不重试；点 verify 前全体格子再查一次 dynamic（最多 5s）兜底。教训：**Google 前端状态机写在 class 上，别用 src 推状态**；真机断言以「每轮错误提示序列」为准（select-more 重复 = 选择未完成），截图提示不是成功判定。

## 9. reCAPTCHA 九宫格（rev3 教训，2026-09-10）

- 同窗口死磕验证必挂：同一窗口连续多轮验证失败后即使选对 Google 也不给过（同会话风控）；maxRounds 上限（默认 3）后必须交任务重试换新窗口
- 点击未注册根因是坐标漂移：页面坐标拟人点击（frame 偏移计算）在真机窗口 92 连续 5 轮未注册；官方 DEMO 用元素原生点击（selenium click 等价）为主，坐标点击只做未注册兜底（rev3 真机批量 10 窗口 grid-click-diag 全部 hit=true 验证通过）
- 网格图必须用原生整图：div.rc-image-tile-wrapper > img 的 src + naturalWidth（300/450 定尺寸）；容器元素截图经 CSS 缩放裁剪后分类乱跳/空数组（窗口 93/100）
- 提示语映射未覆盖直接抛错快速失败（扩充映射表优先于猜测）
- frame 失效防护：Google 换图后旧 Frame 引用可能失效，每轮必须重取 challenge frame
- **九宫格解决后重提交有残留文案误判**（真机窗口 73/80）：widget 变绿后站点残留 "verify that you are not a bot" 文案与 anchor iframe 仍在 DOM——重提交的竞速等待若继续匹配挑战文案/iframe 会立即误判为新一轮挑战而抛错（尽管验证已通过）。重提交必须只等成功文案（arc 任务 `submitAndWait(ctx, false)` 关闭挑战检测）
- **容器截图 fallback 两个硬要求**（真机窗口 83/79）：① 必须按格子数定尺寸（4x4→450x450、3x3→300x300，官方平台按尺寸判图型），恒 300 会分类漏格子（红绿灯只返 2 格→必 select-more）；② 截图前等 1.5-2.5s 动画稳定，动画中截图被平台拒 `ERROR_GARBAGE_SAMPLE`
- **图片质量拒收跳轮不终态**：`ERROR_GARBAGE_SAMPLE`/`ERROR_ILLEGAL_IMAGE`/`ERROR_PARSE_IMAGE_FAIL` 是平台对单张图的拒收，跳过本轮重截即可，不是 captcha_failed 终态（余额/key 错误才是终态）
- **rev3 真机批量结论（2026-09-10，窗口 73-82）**：10/10 全部成功；多个窗口（73/75/79 等）实测走通「v2 挑战 → 九宫格自动选图（原生点击全命中）→ aria-checked 变绿 → 按钮恢复 → 重提交 → 成功文案」全链路；首发失败窗口靠 retry 换新会话恢复（地址校验/网络瞬时失败均自愈）
